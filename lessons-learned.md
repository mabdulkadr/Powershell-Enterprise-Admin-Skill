## How To Use This Register

1. **Before building:** read this file's tail. If a listed lesson applies to the current task, follow its rule.
2. **Append immediately** when any of these happens:
   - The user corrected your output (naming, structure, a rule you got wrong)
   - A delivered script crashed or failed at runtime (PS 5.1 incompatibility, XAML parse error, auth failure, culture-related date bug)
   - You hit a non-obvious pitfall not already in `references/pitfalls.md`
   - You discovered a new environment constraint (PS version, module availability, policy)
3. **Entry format:**

```markdown
## YYYY-MM-DD | <tool name> | <area>
- **Mistake:** what was done wrong
- **Cause:** why it happened
- **Fix:** what actually solved it
- **Rule:** the reusable rule, imperative
```

4. **Rules:** dedupe against this register and `references/pitfalls.md` before appending; entries are evidence-based (no speculation); one line per field.
5. **Promotion:** when a rule has proven itself twice, propose promoting it into `references/pitfalls.md` (ask the user), then log it in the Promotion Archive below.

## 2026-08-25 | Enterprise WPF Tool | PowerShell argument parsing / WPF charts
- **Mistake:** `New-Object System.Windows.Point($cx, $cy - $radius)` crashed at runtime with `[System.Object[]] does not contain a method named 'op_Subtraction'` whenever the OS donut rendered with empty data.
- **Cause:** In `New-Object TypeName(...)` command argument lists, the comma binds tighter than `-`, so PowerShell evaluated `($cx, $cy) - $radius` as array subtraction.
- **Fix:** Parenthesize every computed argument: `New-Object System.Windows.Point($cx, ($cy - $radius))`; verified by isolated reproduction harness.
- **Rule:** Inside `New-Object TypeName(...)` argument lists, always wrap arithmetic expressions in parentheses; static `[Type]::Method(a, b - c)` calls are safe.

## 2026-08-25 | Enterprise WPF Tool | Assembly loading (MSAL interactive auth)
- **Mistake:** `Add-Type -Path Microsoft.Identity.Client.dll` threw `ReflectionTypeLoadException` on Windows PowerShell 5.1, blocking the embedded sign-in window.
- **Cause:** `Add-Type` eagerly enumerates every type in the assembly; MSAL's dependency set (`Microsoft.IdentityModel.*`, Azure.Core) was not yet resolvable.
- **Fix:** Pre-load sibling + parent `Dependencies\` DLLs via `[System.Reflection.Assembly]::LoadFrom`, register a version-agnostic `AppDomain.AssemblyResolve` handler scoped to those folders, then `LoadFrom` the MSAL assembly itself; verified building PCA and `AcquireTokenInteractive().WithUseEmbeddedWebView($true)` on PS 5.1 STA.
- **Rule:** For dependency-heavy third-party DLLs, load lazily with `LoadFrom` plus an `AssemblyResolve` fallback over their directory tree; never `Add-Type -Path`.

## 2026-08-25 | Enterprise WPF Tool | Module discovery / environment constraint
- **Mistake:** Embedded-sign-in setup searched only the primary module's base directory for `Microsoft.Identity.Client.dll` and logged "DLL not found" on machines where that module is a lightweight custom build.
- **Cause:** Custom/renamed admin modules do not vendor MSAL; the assembly ships inside other SDK modules (`Microsoft.Graph.Authentication\Dependencies\Core|Desktop`, `Az.Accounts\lib`, `ExchangeOnlineManagement\netFramework`) scattered across per-edition module roots.
- **Fix:** Search all machine module roots (`Program Files\PowerShell\Modules`, `Program Files\WindowsPowerShell\Modules`, Documents module paths), preferring the edition-matching flavour (`\Core\` on PS7, `\Desktop\` on PS5.1).
- **Rule:** When locating shared third-party assemblies, search across all installed PowerShell module roots and select by PS edition, never assume the calling module vendors them.

## 2026-08-25 | Test-ReadmeFidelity.ps1 (skill tooling) | PS 5.1 parameter defaults
- **Mistake:** `[string]$TemplateDir = (Join-Path (Split-Path -Parent $PSScriptRoot) 'templates')` failed on Windows PowerShell 5.1 with "Cannot bind argument to parameter 'Path' because it is an empty string".
- **Cause:** `$PSScriptRoot` is empty inside parameter default-value expressions on PS 5.1 (set only later in script scope); works in pwsh 7, so pwsh-only testing missed it.
- **Fix:** Declared `$TemplateDir = ''` and resolved it after the param block using the Report-Path-Law fallback chain ($PSScriptRoot -> $PSCommandPath -> $MyInvocation -> cwd).
- **Rule:** Never reference $PSScriptRoot in param() default expressions; resolve script-relative paths after the param block with the standard fallback chain.

## 2026-08-25 | Skill delivery gates | Environment constraint (execution policy)
- **Mistake:** `Test-ToolCompliance.ps1` failed with "AuthorizationManager check failed" inside the Test-Delivery subprocess even when launched with `-ExecutionPolicy Bypass`.
- **Cause:** Skill scripts carried Mark-of-the-Web from download and the machine scope enforces `RemoteSigned`; MOTW files stay blocked for subprocess `-File` launches regardless of the Process-scope bypass attempt ordering.
- **Fix:** `Get-ChildItem <skill-dir> -Recurse -Include *.ps1 | Unblock-File` once per machine; all gates then run green.

## 2026-08-25 | Enterprise WPF Tool | StrictMode + script-scope state
- **Mistake:** New guard variable `$script:EmbeddedSignInActive` was read before any assignment; the first sign-in click crashed with "The variable ... cannot be retrieved because it has not been set".
- **Cause:** GraphCache.ps1 dot-sources `Set-StrictMode -Version 1.0` into the entry scope, so every `$script:` read anywhere in the session requires prior initialization - adding new module state without a top-level default breaks at first use.
- **Fix:** Initialize all new `$script:` state at the owning module's top level (`$script:EmbeddedSignInActive = $false`) and verified with a strict-mode repro (old pattern throws, initialized pattern passes) plus a project-wide assigned-vs-read scan for other candidates.
- **Rule:** When a tool enables Set-StrictMode, every newly introduced `$script:` variable MUST be declared with a default at its owning module's top level before any function reads it.

## 2026-08-26 | enterprise-automation-suite configuration migration | UTF-8 no-BOM breaks PS 5.1 parse
- **Mistake:** After header/logging edits via the file-edit tool, all 6 scripts failed the Windows PowerShell 5.1 parser (missing terminators, unbalanced braces from mid-file) while pwsh's parser reported 0 errors; Test-Delivery smoke output showed a misleading ParseException.
- **Cause:** The editor rewrote files as UTF-8 WITHOUT BOM; 5.1 falls back to ANSI for BOM-less files and misreads multi-byte characters such as U+2713 check marks, whose trailing byte 0x93/0x94 decodes to smart quotes in Windows-1252 and derails tokenization.
- **Fix:** Rewrote every migrated .ps1 as UTF-8 with BOM ([System.Text.UTF8Encoding]::new($true)); all six then parsed clean under 5.1 and passed Test-Delivery.
- **Rule:** Any edit to a PowerShell file containing non-ASCII literals must end with re-verifying the encoding is UTF-8 with BOM before running the 5.1 smoke gate; pwsh parse success proves nothing about 5.1 tokenization of BOM-less files.

## 2026-08-30 | Enterprise Policy Audit Tool | CLI logging / Mandatory parameter
- **Mistake:** `Enterprise Policy Audit Tool.ps1` crashed at the first device-lookup line with `Cannot bind argument to parameter 'Message' because it is an empty string` after a successful Graph sign-in; identical crash recurred on every `Write-Log -Message ""` visual spacer (lines around the device header, policy overview, drill-down summary, investigate/export blocks).
- **Cause:** The script's local `Write-Log` declared `[Parameter(Mandatory = $true)] [string]$Message` and used `Write-Log -Message ""` as a blank-line separator. PowerShell's Mandatory binding treats an empty string as a missing value, so any spacer call crashes before the timestamp/color logic runs - the canonical `scripts/Write-Log.ps1` helper has the same Mandatory constraint, so this pattern crashes every script that copies it verbatim.
- **Fix:** Made the parameter non-mandatory with an explicit empty default and added an early-return guard: `[Parameter(Mandatory = $false)] [AllowEmptyString()] [string]$Message = ""` then `if ([string]::IsNullOrEmpty($Message)) { return }` at the top of the function; visual spacers now no-op cleanly and real messages still hit the timestamp/color logic and log file.
- **Rule:** Any logging helper that is called with `""` as a visual separator MUST declare `Message` as non-Mandatory with `[AllowEmptyString()]` and default `""`, and early-return on empty - the canonical `scripts/Write-Log.ps1` (and the IntunePatterns `Write-Log` it copies) needs the same fix before the next release.

## 2026-08-27 | enterprise library audit | Bulk rename via Python script (no PS regex)

- **Mistake:** Tried to bulk-rename 13 files and their parent folders with regex inside PowerShell one-liners like `Select-String -Pattern '\\$script:remediationResult' -Encoding utf8`; the dollar-sign + backslash inside a PowerShell double-quoted string was parsed as a variable reference and the command failed with `Unrecognized token` or `Illegal \ at end of pattern`.
- **Cause:** Bash/PowerShell quoting around regex backslashes + PowerShell variable expansion inside double-quoted strings is fragile; the model lost time iterating on escape sequences instead of just calling Python.
- **Fix:** Switched the bulk operations to a Python one-liner using `pathlib` + `re` with raw strings (`r'\\$script:remediationResult'`) and a dedicated `*.py` script for multi-step refactors (find/replace, file rename, header edits). All 13 renames + all 836 `$script:camelCase` -> `$script:PascalCase` replacements + all 25 `.PERMISSIONS` normalizations completed without quoting issues.
- **Rule:** For non-trivial bulk refactors across many files, write a Python script to `*.local\share\opencode\tmp\` and run it with `python3 <script.py>`. Reserve PowerShell one-liners for single-file edits where escaping is simple; never try to embed complex regex in a PowerShell -Command string.

## 2026-08-27 | enterprise library audit | Class-method false positive in function audit

- **Mistake:** `Test-ToolCompliance` flagged `ExampleAppDeployerScript.ps1` as having 12+ non-Verb-Noun function names; manual inspection showed they were PowerShell class constructors (`WinGetSource()`) and a method named `Add` inside a `class WinGetPackage` block. The class system requires constructors to share the class name.
- **Cause:** The audit script was a regex on `function <name>` declarations, but PowerShell class methods use the same parser-level `FunctionDefinitionAst` node. There's no reliable AST-only way to distinguish a top-level `function Foo` from a class `Foo()` constructor without walking parent chains.
- **Fix:** Accepted the false positive. The PowerShell language rules mandate that class members (`Foo()` matching class name) and certain method names (`Add`, `Remove`, `op_*`) cannot follow Verb-Noun. Documented in the audit summary; no code change required.
- **Rule:** When auditing PowerShell files for "all functions are Verb-Noun PascalCase", exclude `class` blocks first (parent-aware AST filter or simple text scan for `^class\s+\w+` to mark a region), then count remaining function declarations. Also exclude `Add`, `Remove`, and class-name-matching constructors as valid class members.

## 2026-08-27 | enterprise library audit | Typo in PowerShell class member (`WinGetSource` inside `WinGetPackage`)

- **Mistake:** `ExampleAppDeployerScript.ps1` had a method declaration `WinGetSource ([string[]]$a) { ... }` inside the `class WinGetPackage { ... }` block. PowerShell still parses it (no compile-time check that method names match the enclosing class) but the constructor is dead code - no caller passes a 5-element string array to `[WinGetPackage]::New()`.
- **Cause:** Copy-paste from the preceding `class WinGetSource` definition; the constructor body was correct (`$this.Id`, `$this.Version` etc all match WinGetPackage) but the method name wasn't renamed.
- **Fix:** Deleted the dead method entirely (the equivalent functionality is provided by the 3-arg `WinGetPackage ([string[]])` constructor + `[psobject]` overload already present). No test failure because the method was never called.
- **Rule:** In PowerShell classes, treat any `class-name ()` method as suspicious: it is either a constructor (legit) or a copy-paste mistake. Verify each one is referenced via `[ClassName]::New(...)` somewhere in the same file before keeping it. Same for any `Add`/`Remove` method that has no caller in the file.

## 2026-08-27 | enterprise library audit | `Get-MgGraphAllPage` (typo) coexists with `Get-MgGraphAllPages`

## 2026-08-27 | enterprise library audit | Changelog ordering `1.0` then `1.1`

- **Mistake:** `ExampleAppInventoryScript.ps1` and `ExampleDeviceSyncScript.ps1` had `.CHANGELOG` blocks where `1.1` was placed *after* `1.0` (visually), so the newest-first invariant was broken - the entries were correctly chronologically later, but the file layout made the head look like 1.0.

## 2026-08-27 | HTML report template (skill-wide) | `...` in HTML inside PowerShell here-string breaks parser

- **Mistake:** Tried to truncate a long string with `"...$titleStr..."` inside a PowerShell expression embedded in a `foreach` that built HTML rows. PowerShell interpreted `...` as the range operator (`10..20`), causing "Unexpected token '..' in expression" or "The string is missing the terminator".
- **Cause:** Three dots in a row is the range operator in PowerShell; even inside a string, when adjacent to `$var`, the parser greedily extends the variable name or reads `..` as range syntax.
- **Fix:** Always concatenate: `"$titleStr" + '...'` (or `($titleStr + '...')`). The ellipsis lives outside the interpolation, so the parser never sees `..` adjacent to a variable. Verified by re-running the refactored script's parse and observing zero errors.
- **Rule:** Never write `...$variable...` or `"...$var"` in PowerShell. Use explicit concatenation (`'prefix' + $var + 'suffix'`) or `'{0}...' -f $var`. The 3-dot range operator (`..`) is one of the most common parse-error sources in PowerShell strings, and it's silent until something actually uses the range.

## 2026-08-27 | HTML report template (skill-wide) | Run-ID + UTC + timezone are report fingerprint essentials

- **Mistake:** The first version of the dashboard footer only had the local timestamp. Two reports run 5 minutes apart looked identical in any diff tool, and a tester couldn't tell whether the second run had actually re-collected the data.
- **Cause:** Treating timestamp as a single human-readable string is the easy way, but reports need a machine-distinguishable fingerprint for audit trails and re-runs.
- **Fix:** Footer now includes 4 distinct fields: human-local timestamp (e.g. `2026-08-27 14:32:11`), timezone label (`Arabian Standard Time`), UTC ISO 8601 (`2026-08-27T11:32:11Z`), and a random 8-char run ID (e.g. `A3F7B2E1`). All four are emitted both in the footer DOM and in the text-summary download. The same four fields appear in the header "Generated" line for redundancy.
- **Rule:** Every HTML executive report footer MUST carry 4 fields: local timestamp, timezone, UTC timestamp, run ID. The canonical template at `templates/EnterpriseHtmlReport.template.ps1` exposes them as `-GeneratedAt`, `-Timezone`, `-Utc`, `-RunId` parameters with safe defaults. Any report that omits any of these fails the "audit-ready" gate.

## 2026-08-30 | enterprise-scripts | Inline `if` as cmdlet parameter value

- **Cause:** PowerShell's argument-mode parser treats `(if` as a grouped subexpression only when the `if` is the first token inside the parens; when the parens follow a positional string argument, the parser sees a bare `if` command name. `Write-Log`'s `ValidateSet` on `-Level` did not cause the error — the parser rejected `if` before binding.
- **Fix:** Extracted the ternary to a local variable: `$summaryLevel = if ($bad -gt 0) { 'WARNING' } else { 'SUCCESS' }` then `Write-Log -Message "Completed: $ok succeeded, $bad failed" -Level $summaryLevel`. Verified with 5 smoke tests (`ExampleInventoryScript`, `Clear-DnsCache`, etc.) all exiting 0; swept all 73 scripts to 0 remaining `\(if ($` patterns inside `Write-Log` calls.
- **Rule:** Never pass `if (...) { } else { }` as an inline argument value to a cmdlet — always assign to a local variable first, then pass the variable. `if` is a statement keyword, not an expression, and argument-mode parsing rejects it as a bare command.

## 2026-08-30 | enterprise-library sweep | `2>&1 | Out-String` swallows child output when run inside `&` script

- **Mistake:** Compliance runner script (`run-compliance4.ps1`) reported `Total=208 PASS=0 FAIL=208` for the full library, even though every individual `Test-ToolCompliance` invocation visibly printed `RESULT: COMPLIANT (0 warning(s))` to the host. The runner wrote each file's result to a log file as a "FAIL" line, the operator spent several minutes debugging a phantom regression, and the actual 208/208 compliance state was masked.
- **Cause:** Inside the runner, `& "$skill\scripts\Test-ToolCompliance.ps1" -ToolPath $_.FullName 2>&1 | Out-String` only captures the **stdout + stderr** of the child process. `Test-ToolCompliance` uses `Write-Host` to emit `[PASS]/[FAIL]/RESULT: COMPLIANT` lines; `Write-Host` writes directly to the host's console, not to the success output stream. When piped to `Out-String`, the captured string was empty (Length=0, 0 RESULT lines), so the regex check `($out -match 'RESULT: COMPLIANT')` always failed and incremented the FAIL counter.
- **Fix:** Switched the child-process capture to `*>&1` (all streams including the information stream that `Write-Host` writes to): `$out = & "$skill\scripts\Test-ToolCompliance.ps1" -ToolPath $_.FullName *>&1 | Out-String`. With `*>&1`, `Write-Host` output is captured into the returned string, the regex matches `RESULT: COMPLIANT`, and the runner reports `Total=208 PASS=208 FAIL=0`. Verified by spot-checking 3 known-good files and the empty FAIL list.
- **Rule:** When capturing the output of a child script that uses `Write-Host` (rather than `Write-Output`/`return`), use `*>&1` redirection, not `2>&1`. `Write-Host` writes to the information stream (stream 6), which `2>&1` does NOT include. This applies to Test-ToolCompliance, Test-Delivery, Test-ReadmeFidelity, and any other gate that emits findings via `Write-Host` for color. Add an automated guard: if `$out.Length -eq 0` after the child call, treat it as "capture failed" not "compliant".

## 2026-08-30 | enterprise-library sweep | Half-fix regex left `Mandatory = $true` next to `AllowEmptyString()`

- **Mistake:** First regex sweep over 208 PS1 files used `\[Parameter\(Mandatory = \$true\)\]\r?\n        \[string\]\$Message,` → `\[Parameter\(Mandatory = \$false\)\]\r?\n        \[AllowEmptyString\(\)\]\r?\n        \[string\]\$Message = "",`. The replacement placed the new block correctly, but the **original** `[Parameter(Mandatory = $true)]` line was **also** left in place on the previous line because the regex was non-anchored and the pattern matched `[string]$Message,` but not the full multi-line block. Result: 154 files had a half-fixed signature like `[Parameter(Mandatory = $true)] [AllowEmptyString()] [string]$Message = ""` — which STILL crashes on empty Message because `Mandatory=$true` is preserved and `AllowEmptyString()` only allows the empty string when bound, but Mandatory still treats the empty as a missing value.
- **Cause:** The regex was written to consume only the `[string]$Message,` line and prepend attributes, not to delete the original `[Parameter(Mandatory = $true)]` line. A second pass with the right pattern `\[Parameter\(Mandatory = \$true\)\]\r?\n        \[AllowEmptyString\(\)\]` → `\[Parameter\(Mandatory = \$false\)\]` was needed to clean the residual. Without the second pass, the half-fixed files still crashed at the first spacer and silently failed the gate.
- **Fix:** Ran a second targeted regex sweep on the 154 files that showed the half-fix pattern, replacing `[Parameter(Mandatory = $true)]\n        [AllowEmptyString()]` with `[Parameter(Mandatory = $false)]`. Verified with a post-sweep grep `\[Parameter\(Mandatory = \$true\)\]\r?\n        \[AllowEmptyString` returning 0 hits, then re-ran `Test-ToolCompliance` and confirmed `RESULT: COMPLIANT` for every one of the 154 affected files.
- **Rule:** After any multi-line regex rewrite of a parameter signature, run a SECOND pass that asserts no residual of the original `Mandatory=$true` declaration survives anywhere adjacent to the new `AllowEmptyString()` attribute. The "split regex" anti-pattern (one regex for the new line, one for the cleanup) is fragile; the better fix is a SINGLE anchored regex that consumes the whole block `\[Parameter\(Mandatory = \$true\)\]\s*\n\s*\[string\]\$Message,` and replaces it with the entire new block. The compliance gate catches the final state; the second sweep is the safety net.

## 2026-08-30 | enterprise-library sweep | Here-string `^\)$` regex missed closing paren on continuation line

- **Mistake:** Second OutputPath-Law-12 sweep used a regex `^\)$` to find the end of the `param()` block. The regex matched zero of the 9 target files, so the PSScriptRoot guard was never injected. The first sweep did insert for some files (5/9 succeeded) but for 4/9 the closing paren was on the same line as the last parameter (`[string]$CertificateThumbprint = "")` with the `)` at end-of-line) and the `^\)$` pattern required a line containing only `)`.
- **Cause:** PowerShell allows the closing paren of a `param()` block to be on the same line as the last parameter, especially for single-line parameter declarations like `[string]$Foo = "bar")`. The `^\)$` pattern only matches a line that starts with `)` and has nothing else on it. The hybrid pattern needed: `^\s*\)\s*$` (line with only `)` after trimming) OR `^\s*\[string\]\$[A-Za-z]+ = ""\)\s*$` (closing paren after a string default).
- **Fix:** Replaced the matcher with a state machine: after seeing `^\s*param\(` set a flag, on the next line that is `^\s*\)\s*$` OR `^\s*\[string\]\$[A-Za-z]+ = ""\)\s*$` insert the guard block. Verified 4/4 files that the first sweep missed now contain `$scriptDirectory = if ($PSScriptRoot) { $PSScriptRoot } elseif ($PSCommandPath) { ... }` immediately after the param block.
- **Rule:** Never use `^\)$` as a stand-alone anchor for "end of param block" — the closing paren is allowed on the same line as the last parameter when it has a string default. Use a combined regex that handles both: `^\s*(?:\)|\[string\]\$[A-Za-z]+ = ""\))\s*$`. Better: parse the file into an AST and find the actual `ParamBlockAst` close — `[System.Management.Automation.Language.Parser]::ParseFile($f, [ref]$null, [ref]$errs)` gives you `ParamBlock` with named `Extent` ranges.

## 2026-08-31 | enterprise-scripts HTML Reports | `$_` in `-replace` replacement string causes .NET regex substitution of entire input

- **Rule:** Never pass a string containing `$_`, `$&`, `` $` ``, or `$'` as the replacement argument to PowerShell's `-replace` operator — use literal `IndexOf`/`Substring` insertion or `String.Replace` with a literal replacement instead.

## 2026-08-30 | enterprise-library sweep | `$scriptBase` declared but never referenced = silent Law 12 violation

- **Mistake:** `ExampleAppStatusScript.ps1:982` and `ExampleAppInventoryScript.ps1:981` both contained `$scriptBase = if ($PSScriptRoot) { $PSScriptRoot } elseif ($PSCommandPath) { ... }` but the variable was **declared and immediately abandoned** - no subsequent `Join-Path $scriptBase ...`, no `IsPathRooted` check using it, no branch referencing it. - **Cause:** When the original guard block was added during a previous compliance pass, the developer (or template) wrote the declaration for documentation but never wired the conditional branch that consumes it. There was no test asserting "the declared path-anchor variable is referenced in at least one `if (...) { ... }` branch that touches `$OutputPath`". The gate's pattern was too lenient - matching a *declaration* proves nothing about *behaviour*.
- **Fix:** In both files, replaced the dead `$scriptBase = if ($PSScriptRoot) ...` line with the full canonical Law 12 block that uses the variable: `if (-not $OutputPath -or $OutputPath -eq ".") { $OutputPath = Join-Path $scriptBase "Reports" } elseif ($PSBoundParameters.ContainsKey('OutputPath') -and $OutputPath -and -not [System.IO.Path]::IsPathRooted($OutputPath)) { $OutputPath = Join-Path $scriptBase $OutputPath }`. - **Rule:** When fixing Law 12 (Report Path Law), the gate must assert both *declaration* AND *usage* of `$scriptBase`/`$PSScriptRoot` in a path-resolution branch - not just declaration. Add a check: `Select-String -Path $file -Pattern 'Join-Path\s+\$script(Base|BasePath)?\b' | Measure-Object | ForEach-Object { if ($_.Count -lt 1) { FAIL "Law 12 dead anchor: $file declares $scriptBase but never references it" } }`. The dead-anchor anti-pattern produces a gate PASS but real-world CWD pollution, which is exactly the kind of silent regression the canonical `Initialize-Log` guard prevents for log paths (the lesson is symmetric: log paths AND report paths both need declared-and-used anchors, not just declared).

## 2026-08-30 | enterprise-library sweep | One-regex pattern != canonical-gate; verify by running the gate

## 2026-09-01 | enterprise-scripts | Session discipline — never loop on the same summary

- **Mistake:** After enhancing 2 of 17 reporting scripts (`Get-BatteryHealth`, `ExampleInventoryScript`) with Carbon Dark KPI tiles + bar/donut charts + detailed tables, the model started emitting the same 100-line context block ("Objective / Important Details / Work State / Active / Blocked / Next Move / Relevant Files") on every turn without making a single new edit. Tell me which script to enhance next."). NEVER re-state the same context block; NEVER write a 100-line recap when a 1-line acknowledgment + concrete action suffices.
- **Rule:** A user message that contains no new ask is a signal to advance or pause, not to summarize. The single most expensive behavior in any long session is the model emitting the same context block 50 times. Detect it: if your draft response starts with "Objective:" / "Work State:" / "Active:" headers that match the previous turn, delete the draft and either (a) execute the next action via tools or (b) send a one-line "Ready for the next instruction." # Batch: 2026-09-01 — enterprise-library v2.1 final compliance review (415 files, 224 PS1, 174 MD, 8 SH, 3 JSON)

## 2026-09-01 | enterprise-library v2.1 audit | The canonical gate is the source of truth, not the model's manual sweep

- **Mistake:** The first sweep used a custom regex `Get-ChildItem | Where-Object { (Get-Content -Raw) -match '\[string\]\$OutputPath = "\."' }` to flag 29 files for Law 12 (Report Path Law). A second sweep filtered by `PSBoundParameters.ContainsKey('OutputPath')` and returned 17 "real bug" files. Both sweeps were red flags — the actual canonical `Test-ToolCompliance.ps1` accepts all 29 files as COMPLIANT because it recognizes three alternative guard patterns: `IsPathRooted($OutputPath)` with `Join-Path $scriptBase $OutputPath` is equally compliant as `PSBoundParameters.ContainsKey('OutputPath')` with the same join. The 17-file manual sweep list was wrong.
- **Cause:** When auditing for a specific Law, the natural instinct is to write a quick `Where-Object { -match }` filter that captures the first pattern remembered. PowerShell scripts have many idiomatic ways to express the same intent; restricting the filter to one idiom produces false positives. The canonical `Test-ToolCompliance.ps1` is the audit's source of truth because it was written to recognize the full set of acceptable patterns.
- **Fix:** When `Test-ToolCompliance` returns PASS for a file that a manual sweep flags, sample 3-5 flagged files by re-reading and locating the actual guard pattern. Verified 17/17 by running `Test-ToolCompliance -ToolPath <each>` and confirming `RESULT: COMPLIANT` for all of them.
- **Rule:** The canonical compliance gate (`Test-ToolCompliance.ps1`) is the audit's source of truth. If a manual sweep flag disagrees with the gate, the manual sweep is wrong, not the file. Never mass-edit files based on a custom regex sweep alone; always (1) sample 3-5 flags, (2) re-read the file to confirm the actual guard, (3) run the canonical gate, (4) only edit if the gate also flags. Quick filters are useful for narrowing the search space, not for making changes. Add a note to the audit summary: "X files flagged by regex Y; Y' confirmed by gate; Z files genuinely buggy and edited".

## 2026-09-01 | enterprise-library v2.1 audit | Compliance gate false positive on `Select-Object` substring in `Where-Object` filter

- **Mistake:** `detect-ExampleSecureBootScript.ps1` failed `Test-ToolCompliance.ps1` with `[FAIL] No bare aliases (Law 3) -> 1 suspicious hits` even though the script uses `Select-Object` (full cmdlet name) in a WMI fallback path. Manual inspection found zero bare aliases.
- **Cause:** The gate's alias regex pattern `(?<![-\w])(gci|select|where|...)(?![-\w])` matches the substring `select` inside `Select-Object` because the lookbehind requires a non-word char (or BOL) before `select` — but `Select-Object` has `S` (uppercase, still a word char) before it, and the case-insensitive match catches `Select` even in cmdlet names. The regex correctly flags prose containing the word "select" but incorrectly flags cmdlet names too.
- **Fix:** The script is a real false positive (uses `Select-Object` as a full cmdlet name, not the `select` alias). Accepted the FAIL — manual review confirmed the script has no actual bare aliases. No code change. This is the same class of false positive as the `where` prose flagged in 2026-08-30 (`Send-EmailNotification.ps1`).
- **Rule:** The bare-aliases gate is intentionally aggressive to catch prose abuse, but it WILL false-positive on `Select-Object`, `Where-Object`, `gci` substrings inside other cmdlet names. When a FAIL is the result of `Select-Object`/`Where-Object`/`Compare-Object`/`Group-Object`, manual review confirms it's not a real alias. To make the gate cleaner: use a word-boundary-only regex `(?<!\w)(?:gci|select|where|...)(?!\w)` (note: `\w` already includes `_`, but the trailing `-(?:` accepts the dash for `Select-Object`). Until then, this false positive rate is acceptable; document the false-positive class so the next maintainer doesn't edit a correct script.

## 2026-09-01 | enterprise-library v2.1 audit | `bash` tool strips/corrupts emoji bytes when piping here-strings through `Set-Content`

- **Mistake:** Tried to write 11 v2.1 README files by piping large here-strings through `Set-Content -Encoding UTF8` in the PowerShell `bash` tool. The emojis (✨, 📂, ⚙, 🛡, 👤, 📜, ⚠, 🚀, 🔎, 🛠, 🧭, 🔧, 🔐, 🔑, 🔥, 🔍, 💻) were silently stripped or replaced with `?` / `??` placeholders. One file (`ExampleSecureBootScript\README.md`) ended up at 4955 bytes with `0xBF 0xBF` byte sequences where emojis should have been, and the `Read` tool failed with `Cannot read binary file`.
- **Cause:** The `bash` tool (which runs `pwsh`) interprets some Unicode characters in the input stream as a fallback character when the input is not a known PowerShell escape. The here-string piping path silently dropped or substituted bytes for the first emoji in each line. The bash tool's stdin/stdout is text-mode; multi-byte characters in the input are sometimes subject to locale fallback (e.g., the emoji is interpreted as bytes in CP1252 and lost when the encoding tag on the redirected stream is misread).
- **Fix:** Re-wrote every README using `[System.IO.File]::WriteAllText($f, $content, [System.Text.UTF8Encoding]::new($false))` and constructed the content with `[string][char]::ConvertFromUtf32(0xHHHH)` for each emoji codepoint. Defined a small helper `function H($c) { [string][char]::ConvertFromUtf32($c) }` and used `$ICON_F = H(0x2728); $ICON_S = H(0x1F4C2); ...` then built strings via `"$ICON_F Core Features"`. Verified with `[System.IO.File]::ReadAllText($f, [System.Text.Encoding]::UTF8)` + `Select-String -Pattern '✨|📂'` returning 1+ hits per README, and a hex byte check `0xE2 0x9C 0xA8` for the `✨` sequence.
- **Rule:** When writing files from the `bash` tool in this skill, NEVER pipe a here-string containing emojis into `Set-Content`. Use the canonical pattern: build the full file in a string variable (`$content = "..."` where the string is built via concatenation with `[string][char]::ConvertFromUtf32(0xHHHH)` for each emoji), then `[System.IO.File]::WriteAllText($path, $content, [System.Text.UTF8Encoding]::new($false))`. The `UTF8Encoding::new($false)` produces UTF-8 *without* BOM; `Set-Content -Encoding UTF8` is unreliable in the `bash` tool. This rule is now Rule #1 in the "Hardcoded Rules From The Lessons Learned Register" section of `SKILL.md`.

## 2026-09-01 | enterprise-library v2.1 audit | `Test-ReadmeFidelity` exit code is consumed by `& $script | Out-String` pipe — use `$null = & $script` or `; $LASTEXITCODE`

## 2026-09-13 | Intune-Proactive-Remediations audit | `Get-ItemPropertyValue` on a missing registry value throws terminating `PSArgumentException` even with `-ErrorAction SilentlyContinue`

- **Mistake:** `repair-Repair-KB5124008SecureChannel.ps1` crashed (exit 2, `Status: Error`) before writing any fix, and `detect-Enable-MultiSession.ps1` would have crashed on devices where `fSingleSessionPerUser` is absent (the default compliant state) — both relying on `Get-ItemPropertyValue ... -ErrorAction SilentlyContinue` to return `$null` when the value is absent. Also visible in the sibling `Repair-KB5124008SecureChannel` detection's isolation DEBUG read path on a patched device.
- **Cause:** `Get-ItemPropertyValue` throws a **terminating** `PSArgumentException` (full ID: `Microsoft.PowerShell.Commands.GetItemPropertyValueCommand.PropertyDoesNotExistException`) when the named value is absent from the key. `-ErrorAction SilentlyContinue` cannot suppress terminating errors; the exception propagates past `catch [ItemNotFoundException]` to the generic catch or MAIN catch, producing exit 2. In contrast, `Get-ItemProperty` returns the `PSCustomObject`/`RegistryKey` and the missing property simply resolves to `$null` via normal member access — no terminating error.
- **Fix:** Replaced every runtime `Get-ItemPropertyValue -LiteralPath $p -Name $n -ErrorAction ...` read with the null-safe two-step: `(Get-ItemProperty -LiteralPath $p -ErrorAction Stop|SilentlyContinue).$n`. Files corrected: `detect-Enable-MultiSession.ps1` (CHECK 1 + CHECK 2), `remediate-Enable-MultiSession.ps1` (Test-FixApplied + two MAIN current reads), `detect-Repair-KB5124008SecureChannel.ps1` (isolation DEBUG read), `remediate-Repair-KB5124008SecureChannel.ps1` (Test-FixApplied + MAIN current read). Verified: `Repair-KB5124008SecureChannel` remediation now runs the full pre→fix→verify→JSON pipeline instead of crashing (exit 1 with honest "Administrator rights required" per-target warnings in the non-elevated test shell — correct behavior).
- **Rule:** Never use `Get-ItemPropertyValue` in scripts that must tolerate absent registry values (Intune remediations, idempotent tools). Use `(Get-ItemProperty -LiteralPath $path -ErrorAction Stop|SilentlyContinue).$name` — member access on a missing property returns `$null` silently with no terminating error. If the *path itself* is absent, guard with `Test-Path` first or use `-ErrorAction SilentlyContinue` (which *does* suppress non-terminating path-not-found errors). Update `references/pitfalls.md` if the `Get-ItemPropertyValue` command is added to the forbidden pattern list.
